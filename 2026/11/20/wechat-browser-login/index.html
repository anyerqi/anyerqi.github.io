微信浏览器快捷登录：按流程拆解

实测环境：Windows 微信 4.2.1.8、macOS 微信 4.1.15、Edge / Chrome。文中数据来自本机抓包、内存转储与 API Hook。

微信网页登录有两种形态：扫码，和「本机已登录，直接授权」。后者不经过二维码，靠的是一个只监听 127.0.0.1 的 HTTPS 服务。本文按流程图的顺序，一步一步拆这条链路。

全流程

sequenceDiagram
  participant U as 用户
  participant P as 网站页面
  participant L as 本机微信
  participant W as 微信服务端
  participant B as 网站后端

  Note over L: 第 0 步（前提）桌面客户端已登录
  U->>P: 第 1 步 点击「微信登录」
  P->>P: 第 1 步 创建 iframe
  P->>L: 第 2 步 探测 14013 / 14014 / 14015
  P->>L: 第 3 步 TLS 握手
  P->>L: 第 4 步 POST /api/check-login
  L-->>P: 第 5 步 昵称、头像、authorize_uuid
  U->>P: 第 6 步 点击「快速登录」
  P->>L: 第 7 步 POST /api/authorize
  L->>W: 第 8 步 MMTLS 转发授权
  W-->>L: 第 8 步 授权结果
  L-->>P: 第 9 步 redirect_url（含 code）
  P->>B: 第 10 步 跳转 redirect_uri
  B->>W: 第 11 步 用 code 换 access_token
  W-->>B: 第 11 步 返回 openid

下面逐步说明每一步在做什么、为什么必须这么做。

第 0 步（前提）：桌面客户端处于登录态

这一步不在图里，但它是整条链路的前提。

只有桌面微信登录完成后，本机端口才开始监听。 客户端停在登录窗口（窗口类名 mmui::LoginWindow）时，14013 等端口全部不监听；期间打开 wx.qq.com、调用 weixin:// 协议、重启客户端、打开第三方登录页，都触发不了。

手机确认登录后，五个端口同时进入 LISTENING：14013、14016、14019、14022、14023。

浏览器里的网页登录只消费这些端口，不会唤起它们。换一台没有登录桌面微信的电脑，快捷登录一定不可用，页面只能退回扫码。

第 1 步：页面点击「微信登录」

网站不自己实现协议，而是引入微信开放平台提供的网页登录 JS 库——wxLogin.js（https://res.wx.qq.com/connect/zh_CN/htmledition/js/wxLogin.js），在页面上用 new WxLogin({ appid, scope, redirect_uri, state }) 初始化。

页面与 iframe 之间用 postMessage 通信：iframe 通过 status 消息回传 wxReady、wxQRcodeReady 等状态，网站据此决定何时显示登录按钮。

用 iframe 而不是让网站自己发请求，是为了把登录协议收在微信自己的源里：网站只拿到最后的结果，不接触中间的 authorize_uuid 和本地接口。

第 2 步：探测本机端口

iframe 里的页面按固定顺序探测 14013 → 14014 → 14015，逐个尝试 https://localhost.weixin.qq.com:<port>。

  • 命中条件不是「端口能连上」，而是「能完成 TLS 并且认登录接口」。
  • 多个端口是为了回退：端口被占用、或机器上装了多个微信版本时，仍有可用入口。
  • 实测登录后本机同时监听多个端口，其中 14016 / 14019 / 14023 用同一张证书但不接受登录接口，属于同一套本地服务；14022 不是 TLS，握手直接断开。

第 3 步：TLS 握手，以及为什么需要域名和证书

这一步是整套方案里最容易被忽略、但设计上最关键的一环。

为什么必须是 HTTPS。 不是为了加密，是为了身份。127.0.0.1:14013 没有任何访问控制：任何本地程序都能抢在微信前面绑定它，收下页面发来的 appid、redirect_uri、state，再返回一个自己的 redirect_url。页面没有办法分辨对面是谁。TLS 证书是唯一的辨别手段——本地接口没有共享密钥，也不走账号体系。

浏览器这一侧的要求。 除了「证明对面是谁」，这段连接还要满足浏览器的几条规则：

  • 跨源读取：页面源是 https://open.weixin.qq.com，本地端口是另一个源。响应必须带 Access-Control-Allow-Origin: https://open.weixin.qq.com，否则页面读不到 JSON，只能拿到一个不透明响应。
  • 本地网络访问权限：新版 Chrome 把「公网页面访问本地网络」单独设为一项权限，iframe 必须声明 allow="local-network-access"，否则请求在浏览器侧就被拒绝。
  • 安全上下文：回环地址在规范里被视为「潜在可信来源」，所以明文 http://127.0.0.1 在多数浏览器上并不会被当作混合内容拦截。这也是为什么「加密」不是选 HTTPS 的主因——主因仍是身份。但各浏览器对私有网络请求的安全要求在收紧，明文回环属于随时可能变的实现细节，而公共证书的 HTTPS 在所有环境下都成立。

为什么必须有域名。 公共 CA 不给 localhost、*.localhost 或 127.0.0.1 这类保留名和保留地址签发证书。腾讯需要一个自己控制、能通过域名验证的名字，于是用了 weixin.qq.com 的子域 localhost.weixin.qq.com，并把它解析到 127.0.0.1。名字足以申请证书，解析结果又把流量锁在本机。

为什么必须是公共 CA。 自签证书不在系统信任库，浏览器会拦下并弹警告，快捷登录就无法无人值守完成。用公共 CA 的 OV 证书，浏览器默认信任，页面才能静默完成这次本地调用。

证书实测数据：

项 值
主体 CN=localhost.weixin.qq.com，O=Tencent Technology (Shenzhen) Company Limited
签发者 DigiCert Secure Site OV G5 TLS CN RSA4096 SHA384 2022 CA1
算法 RSA-2048
序列号 0AE9E711B11E33C15FB5F9E56DF9B008
有效期 2026-11-18 至 2027-06-04
证书透明度 该域名仅一条签发记录

只有一张证书，意味着所有客户端出示同一张，私钥必须分发到每一台机器。这违背公共 CA 对私钥保管的基本要求，是这套设计最薄弱的地方——客户端为此付出的代价见文末。

第 11 步：网站后端兑换凭证

最后一步与浏览器无关。网站后端拿 code 调 api.weixin.qq.com，换取 access_token 和 openid。

access_token 不下发到前端，前端从头到尾只见过 authorize_uuid 和一个一次性的 code。

证书与私钥在客户端里的形态

前面说「所有客户端共用一张证书」，那私钥是怎么到客户端的？实测结果和直觉不同：

  • 握手前进程里没有证书。登录后、任何握手前抓全内存，证书 DER 与模数命中数为 0。
  • 握手时证书只出现在发送缓冲区。命中位置能看到完整 TLS 记录：16 03 03 … 0b 加证书消息。
  • 私钥不驻留。握手后按 OpenSSL BIGNUM 的 64 位和 32 位小端两种排布搜模数，命中数为 0。
  • 握手期间零文件 I/O。挂 NtCreateFile，握手前后调用计数完全不变。
  • 握手期间没有网络收发。把微信出站整个封掉，握手照样完成。
  • 不走 Windows 证书体系。CryptAcquireCertificatePrivateKey、CryptSignHashW、BCryptSignHash 调用次数均为 0；Cert:\CurrentUser\My 与 LocalMachine\My 里也没有这张证书。
  • 登录阶段也看不到证书明文。扫描 68,000 多次堆分配，用 DER、PEM、以及该证书独有的 base64 指纹三种编码检索，命中数为 0。

由这些事实可以推出：证书与私钥在客户端登录阶段以非明文形式进入进程，每次握手时临时解出、签名、清掉。磁盘、注册表、证书存储、钥匙串里都没有它，但每次握手都能完成。

安全边界

  • 页面能拿到的只有 authorize_uuid 和最终的 code。code 由服务端签发，本地服务伪造不了。
  • 本地 HTTPS 解决两件事：让页面确认「对面是不是微信」，以及让这段跨源请求落在浏览器认可的安全上下文里。账号认证仍然由服务端完成。
  • 由于私钥全客户端共用，它保护的是回环地址上的一个身份，不是用户凭证。
  • 快捷登录依赖客户端登录态，客户端没登录时，页面只能退回扫码。

小结

这条链路可以压缩成一句话：页面按约定端口找到本机微信，本机微信把已登录账号换成一张一次性票据，服务端再把票据换成 code，最后由网站后端兑换凭证。

端口开不开取决于桌面客户端是否登录；域名和证书则用来在这个谁都能占用的回环端口上，证明对面确实是微信。
